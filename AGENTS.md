# Working on Halderworks Instrument

This file is for anyone changing the system: a person or an agent editing tokens, rules or tools.
An agent *using* the system to build a product screen reads [SKILL.md](SKILL.md) instead.

## Layout

| path | what it is |
|---|---|
| `design/` | the book: the foundations, one file per subject, each rule naming the file that enforces it, and [design/64-component-sheets.md](design/64-component-sheets.md), generated. [design/00-brand-book.md](design/00-brand-book.md) opens it and holds what the house admits, partly answers and declines |
| `ramps/` | the source of every token value. `brands/<name>.json` is a brand: a neutral, five to eight named hues, and optionally a shape register, an icon stroke and a face per family. `roster.json` holds the registers, strokes and faces a brand may name, each face pinned by the sha256 of its file and its OFL text. `tokens/<name>.tokens.css` is generated from a brand by `tools/ramps.py` and never edited by hand. `roles.css` is the colour roles every brand shares, and `scales.css` the rem type, space and control scales, the `data-text-size` setting, the density, touch and reduced-motion blocks and the constants every brand shares. `tools/contrast.py` certifies `roles.css` and refuses any block in it that is not colour, which is why the scales are a file of their own |
| `exports/` | generated by `tools/export.py` from `ramps/tokens/house.tokens.css`, `ramps/roles.css` and `ramps/scales.css`; never edited by hand. `tests/exports.py` cascades them in every theme, contrast, pointer, motion and text-size condition |
| `examples/` | one directory per product brand, holding the `exports/` that `tools/export.py examples/<name>` writes from `ramps/tokens/<name>.tokens.css`. CI exports and certifies every one on every change; each product owns the copy it ships, and papertrace syncs its copy from `examples/papertrace/exports/variables.css`, so that path is a consumer's |
| `fonts/` | the house faces, Archivo, Literata and IBM Plex Mono, as WOFF2 with each face's `OFL.txt`, and `fonts.css`, which loads them from the same origin. `tools/faces.py --vendored` holds every file to its pin in `ramps/roster.json` |
| `components/` | the component layer: `components.css` over the exported roles and scales, `radiogroup.js` (its one script), `catalogue.py` (the one source for every sheet), the Lucide icons the sheets use with their ISC `LICENSE`, and, generated by `tools/components.py` and never hand-edited, `sheets/<group>.html` and the sheets in [design/64-component-sheets.md](design/64-component-sheets.md). A sheet opened with `?brand=<name>` draws from that brand's exports. `renders/` holds a WebP of each group at M in both themes, stamped against the files it pictures |
| `tools/` | ten standard-library Python 3 scripts, no dependencies. Only `check-sources.py` uses the network, and only `painted.py` needs a browser |
| `tests/` | the suite that checks the tools rather than the tokens, adopted from the 2026-09-21 audit; `tests/run.py` is the one command |
| `.github/rulesets/`, `.github/settings/` | what this repository enforces on the forge, as files. Nothing applies them on its own; see "The settings that are not files" below |
| `scripts/apply-repo-settings.sh` | the one command that sends those files to GitHub |
| `docs/publication-record.md` | the one-off record of the first publication; not maintained |
| `docs/brand-tier-record.md` | the one-off record of the first browser render of the three product brands, from a specimen page since retired; not maintained |

## The tools, which are the checks

Python 3, no dependencies. Only `check-sources.py` uses the network.

```bash
python3 tools/ramps.py            # ramps/brands/*.json -> ramps/tokens/<name>.tokens.css
python3 tools/ramps.py --check    # emit nothing; fail if a brand no longer builds, misses a floor, or its file is stale
python3 tools/contrast.py         # every ramps file and ramps/roles.css, certified by the second instrument
python3 tools/export.py           # regenerate exports/ and refuse if it diverges from its sources
python3 tools/export.py examples/papertrace   # the same, per brand
python3 tools/distinct.py         # how far apart the brands paint
python3 tools/faces.py --vendored # fonts/ holds exactly the pinned files, and fonts.css loads only them
python3 tools/components.py --check  # the component sheets match catalogue.py and components.css, and the renders their stamp
python3 tools/check-links.py      # every internal link and anchor in every Markdown file
python3 tools/test-check-sources.py  # the source classifier, against a local server
python3 tools/painted.py          # every pair contrast.py certifies, rendered in headless Brave and measured on the screenshot
python3 tools/check-sources.py    # every cited source still resolves. THE ONE THAT LEAVES THE MACHINE
python3 tests/run.py              # the checks on the tools: invariants, mutations, ramps, exports, components
python3 tools/faces.py --check FONT... OFL.txt...  # a roster face: x-height, pitch, sha256 and licence text, against copies of its files
```

CI exports every directory in `examples/` rather than naming them, and `tools/contrast.py` and
`tools/distinct.py` read every file in `ramps/tokens/`, so a new product brand is covered by adding
its brand file and its directory.

`check-sources.py` is the weekly job's and is not run per change; everything above it is, except
`painted.py`, below. `check-sources.py` answers in three classes rather than two, and the middle one
is the point: `ok` for 2xx/3xx, `refusing` for 401/403/429 - a server answered, so the source exists
and only access from a data-centre address is gated - and `dead` for 404, 410, any other error
status, or no response at all. Only `dead` fails. What it treats as a citation in the first place is
narrower than every URL in the tree: a URL inside a fenced code block is an example the book prints,
not a source it stands behind, so a `preconnect` hint, a CDN base or an XML namespace is never
probed. `test-check-sources.py` holds both lines against a local `http.server` and a closed port, so
a merge cannot quietly widen or narrow either.

`painted.py` needs a Chromium (Brave first, `--browser PATH` for another) and a sandbox that lets
it bind its profile's singleton socket, so it is a local and release check and CI does not run it.
**Read a browser's colours from a screenshot, never from a canvas.** Brave randomises
`getImageData` on http origins by up to one code value per channel, so `#FFFFFF` can read back as
`254,254,254`. A label that paints at 4.521:1 read back anywhere from 4.432 to 4.531, and that is
how step-9 solids were once reported under 4.5:1 in the browser when the pixels were exact
([the evidence file as it stood on 2026-10-02](https://github.com/Abhijeet34/halderworks-design/blob/a95ed0fed0c544fc12483031a2066f3eecc6b535/design/90-evidence.md#contrast-read-from-a-browser)).
`painted.py` reads `Page.captureScreenshot` for this reason.

The tools above check the token set. `tests/run.py` checks the tools, because a refusal
nobody has watched fail is a refusal nobody has tested: the 2026-09-21 audit ran 21 mutation
cases against this repository and 17 wrong inputs left every tool green.
`tests/invariants.py` holds the two instruments apart and in agreement, and
`tests/mutation_tests.py` runs a set of deliberately wrong inputs (its own run prints "N cases: N
as expected, 0 improved, 0 failed" for the current count); one further diagnostic,
`tests/ident_sweep.py`, prints rather than refuses and is run on demand. `tests/ramps.py` (205 seconds on 2026-10-02) checks `tools/ramps.py` from outside:
`contrast.py` certifying the committed files, every accent hue building, malformed brand and
roster files refused by name, and `contrast.py` refusing a floor missed by under 0.01, a role on
the wrong step, an accent equal to the success green, a chart series under its mark floor or on
another series or a state, a shape or face outside the roster, and a malformed file.

**Validating through no-mistakes, name every suite in `SUITES` in `tests/run.py` as its own
command, never `tests/run.py` itself:** `tests/invariants.py`, `tests/mutation_tests.py`,
`tests/ramps.py`, `tests/exports.py`, `tests/components.py`, and any suite added there since. The
aggregate takes several minutes, and the pipeline's test agent backgrounds a run longer than about
3 minutes and returns before it finishes, so its verdict rests on output that never arrived
(measured on PRs 23 to 28). Each suite in the foreground, with an explicit timeout of at least
600000 ms, never backgrounded, is evidence; the aggregate there is not.

`ramps.py` and `contrast.py` are deliberately two instruments rather than one, and two things make
them two. They share no arithmetic: `ramps.py` uses Ottosson's published Oklab constants,
`contrast.py` the CSS Color 4 reference path a browser implements, and `contrast.py` carries the
CIEDE2000 for the painted separation bars, held to the published Sharma test pairs by
`tests/invariants.py`. And they read different declarations of what must hold: `ramps.py` solves
against its own step floors, `contrast.py` carries its own floors, bars and list of every role it
certifies and never imports `ramps.py`, so a floor cannot be weakened in the same edit as the value
it guards. A build that passes while a contrast run fails means one of them is wrong, and that is a
disagreement one instrument checking itself can never report.

Both are built to one rule, stated in the code where it is enforced: **measure the artifact, never
the intent.** A value that was not re-measured in the exact form it will ship has not been
certified, so `ramps.py` parses the CSS it is about to write and measures it again, and
`contrast.py` measures every pair twice - on the float value and on the 8-bit value a display
receives.

A product's identity is a brand file, never a hand-pick ([design/12-brand.md](design/12-brand.md)),
built by the same code as the house's and certified by the same second instrument:

```bash
python3 tools/ramps.py            # writes ramps/tokens/papertrace.tokens.css from ramps/brands/papertrace.json
python3 tools/contrast.py ramps/tokens/papertrace.tokens.css
python3 tools/export.py examples/papertrace
```

An accent the bars refuse is refused by name: at hue 150 `--hw-accent-fill` sits 0.4 CIEDE2000
from `--hw-success-fill` in light, against the 5
[design/12-brand.md](design/12-brand.md#the-bars-every-brand-is-held-to) requires, and
`contrast.py` refuses it, which is what makes "a product cannot take hue 150" an executable rule
rather than a sentence.

## Rules a change is held to

- **Never redefine an `hw-` token.** A product extends in its own namespace, `--quoth-`, `--gates-`,
  and takes its identity from a brand file, which names hues, a register, a stroke and faces,
  and never a token.
- **A new token needs four things**: a name in the scale it belongs to, a usage note saying where it
  may and may not be used, a number with a derivation, and its row in the verification. A colour is
  a role in `ramps/roles.css` naming a ramp step, which `tools/contrast.py` must certify or exempt
  by name; a size, space, layout or motion token joins its family in `ramps/scales.css` with its
  description as the comment beside it, and `tests/exports.py` holds a space or size to the unit.
- **A component belongs in the house when two products need it.** It is an entry in
  `components/catalogue.py` and the rules in `components/components.css` that name its classes;
  `tools/components.py` writes its sheet and its live page, and its renders are taken as in
  "Re-rendering the component sheets" below.
- **A roster face is OFL-1.1, pinned by the sha256 of its upstream TTF and of its `OFL.txt`.**
  `tools/ramps.py` refuses any other licence; after editing an entry, run `tools/faces.py --check`
  on fresh copies of both files ([design/20-type.md](design/20-type.md#the-licence-rule)). A face
  the house ships is vendored in `fonts/` and pinned by its `vendored` entry, which
  `tools/faces.py --vendored` holds.
- **Never hand-edit `ramps/tokens/`, `exports/` or `examples/*/exports/`.** All three are
  generated. Edit the brand file, `ramps/roles.css` or `ramps/scales.css` and rebuild.
- **A gap is a finding, not a blocker.** Ship the screen with the nearest house value and say in
  the same breath what you needed.

Run the per-change tools and `tests/run.py` before opening a pull request; CI runs the same ones
and a merge depends on them. [`.github/workflows/consistency.yml`](.github/workflows/consistency.yml) is their single
definition, and both [`ci.yml`](.github/workflows/ci.yml) and
[`maintenance.yml`](.github/workflows/maintenance.yml) call that one file rather than carrying a
copy each.

A change to the book keeps `tools/check-links.py` at 0 unresolved, and keeps the book to
foundations and generated sheets: a foundation rule names the file that enforces it, or says that
no file does, and a component is documented only in its entry in `components/catalogue.py`, never
a second time by hand in `design/`. The book held 7,506 lines of hand-written component and
pattern prose, and one read found 35 places where it disagreed with itself or with the tokens;
`tools/check-coverage.py`, which held a `covered-by` comment beside every refusal and every copy
of four counts, kept the counts consistent while the content drifted, and retired with that prose.

A source the book relies on is named in a Sources table in the file that relies on it, with what
was taken from it and what was left; a source screened and refused gets its row there too, with
the reason and what would change the answer. The full evidence and decline records, the source
ledger the system's owner supplied included, are
[design/90-evidence.md](https://github.com/Abhijeet34/halderworks-design/blob/a95ed0fed0c544fc12483031a2066f3eecc6b535/design/90-evidence.md) and
[design/85-considered-and-declined.md](https://github.com/Abhijeet34/halderworks-design/blob/a95ed0fed0c544fc12483031a2066f3eecc6b535/design/85-considered-and-declined.md) as they stood on
2026-10-02, before the book was cut; they are dated records and are not maintained.

## What a merge depends on

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on every pull request, on Linux, with
no path filter. It has four jobs: the fleet's two shared scans from `Abhijeet34/gates`, the
`consistency` call described above, and a `checks` aggregate that `needs:` the other three and
refuses any result that is not `success`.

**`checks` is the only required status context**, named in
[`.github/rulesets/main.json`](.github/rulesets/main.json). Jobs can be added or renamed in
`ci.yml` without touching branch protection, which is the whole reason the aggregate exists. The
converse is the trap: a context required by the ruleset that no workflow publishes blocks every
pull request forever, so **`ci.yml` ships first and the ruleset follows only once the context has
been seen reporting on a real pull request**.

## What `@main` on the shared gates buys and what it costs

`ci.yml` calls two workflows from `Abhijeet34/gates` at `@main`, which is a moving ref: what
gates this repository can change with no commit here. That is a deliberate call, and these are
the numbers behind it.

**What a hostile change to `gates` `main` would get.** Both calls run under the caller's
`permissions: contents: read`, a called workflow cannot raise its own permissions above the
caller's, and neither call passes `secrets:`. So the reachable outcome is a read-only token on a
public repository, which is nothing, and a false green on the secret scan and the watermark scan,
which is the real exposure. `gates` has one collaborator, its `main` carries ruleset `23545843`
with no bypass actors, required signatures, a pull request and a required `checks` context.

**What pinning would cost.** `shared-secret-scan.yml` hard-codes the sha256 of the canonical
`.gitleaks.toml` and `.githooks/pre-push` and fails any caller whose synced copies differ. A
caller pinned to a SHA keeps matching the digests of the day it was pinned, so the drift check
the shared workflow exists to perform is switched off in exactly the repository that most needs
it. A pin also freezes the scanner: a detection bug fixed upstream never reaches a pinned caller,
and a stale gate reports green for the same reason a hostile one would.

So: keep `@main`, and treat `gates` `main` as part of this repository's trusted computing base
rather than as a third-party dependency. The residual gap is a `gates` change that lands between
a green run and a merge; the ruleset's `strict_required_status_checks_policy: true` covers
staleness of this repository's branch and nothing covers that, so a re-run before merge is the
only control and it is a person's to apply.

**What would change the answer**, any one of them: `gates` gains a collaborator or a bypass actor
on `main`, a call here starts passing `secrets:` or needs a permission above `contents: read`, or
`gates` stops being owned by the same account. At that point the shared workflows become a
third-party dependency and get pinned by SHA, with a scheduled job to compare the pin against
`main` so the drift detection is replaced rather than dropped.

## The settings that are not files

`main` is protected by a ruleset, not by the older branch-protection API, and the ruleset lives in
the tree:

```bash
scripts/apply-repo-settings.sh Abhijeet34/halderworks-design
```

It sends `.github/rulesets/main.json` and the four files under `.github/settings/`, and it is
idempotent - a ruleset whose name already exists is updated in place, and the name is the join, so
renaming one in the file creates a second on the forge. It sends whatever is in the working tree,
so run it only from a tree whose settings files are the ones you intend.

Editing one of those files changes what this repository *says* it enforces. It changes what GitHub
*does* enforce only when somebody runs that command. Read the live state back afterwards:

```bash
gh api repos/Abhijeet34/halderworks-design/rulesets
gh api repos/Abhijeet34/halderworks-design/rules/branches/main
gh api repos/Abhijeet34/halderworks-design/branches/main --jq .protected
```

**Not `branches/main/protection`.** That is the older branch-protection API and it does not read
rulesets: with the ruleset live and all five rules enforcing, it still answers
`Branch not protected (HTTP 404)`, which reads exactly like an unprotected branch. `rules/branches/main`
lists the rules that actually apply, each with the ruleset id it came from.

Two more things measured rather than assumed, because both look like a broken setup otherwise:

- `gh-axi api` sends only `--field key=value` and has no flag for a JSON request body, so it cannot
  apply a ruleset. `scripts/apply-repo-settings.sh` uses `gh api --input` for that reason.
- GitHub fills `require_extra_approval_for_unattributed_changes: true` into the `pull_request` rule,
  a key `.github/rulesets/main.json` does not carry. A file that mirrored the response back could be
  refused by the endpoint that applies it, so the file stays as written and the live read carries
  one extra key.

## The weekly maintenance job

[`.github/workflows/maintenance.yml`](.github/workflows/maintenance.yml) runs every Monday and on
demand, on Linux, with no secrets beyond the repository's own token. **It opens an issue only when
something has actually moved**, so a quiet week is silent rather than noisy.

**What it checks.** Every row but the last is the `consistency` call, which `ci.yml` makes on every
pull request as well; only the last row is the weekly job's own, because only a schedule can catch
a source that went away without anyone touching this repository. That is also why this workflow
has no `push` trigger: `ci.yml` already runs the consistency call on every push to `main`, and a
per-push network sweep is 52 outbound requests (counted on 2026-10-02, after the book was cut to
foundations) against a field that moves in months.

| check | how it fails |
|---|---|
| every brand still builds from its file | `ramps.py --check` refuses a brand or roster file, finds a step floor missed, or finds a committed file in `ramps/tokens/` the brand does not produce |
| every brand's ramps and roles still hold | `contrast.py` finds a step floor or solid label under its bar, a role in `ramps/roles.css` under its bar or certified by nothing, a CIEDE2000 bar missed, a shape, stroke or face outside the roster, a dark override its `prefers-color-scheme` copy disagrees with, or a malformed file; `distinct.py` finds two brands that paint as one |
| every vendored face is the pinned file | `faces.py --vendored` finds a file in `fonts/` off its sha256, an `OFL.txt` off its licence pin, a file the roster does not account for, or `fonts/fonts.css` loading anything else |
| every space and size value is on the 4px unit or declared | `tests/exports.py` finds an undeclared off-unit value at M, or a declared exception that has moved back onto the unit |
| every export still matches its source | `export.py` exits non-zero, or regenerating `exports/` or a brand's exports leaves anything in `git status --porcelain` |
| every refusal the system depends on still refuses | `tests/run.py`: the two instruments share code or stop agreeing, a buildable accent hue emits ramps `contrast.py` refuses, or a deliberately wrong input leaves every tool green |
| every component sheet is current | `components.py --check` finds a sheet that no longer matches `components/catalogue.py` and `components.css`, or a render older than its stamp |
| every internal link and anchor | `check-links.py` finds a link, in any Markdown file in the repository, to a file or a section that does not exist |
| every cited external source still resolves | an HTTP request per distinct URL in the book, failing on 404, 410, any other error status, or no response. A 401, 403 or 429 is reported as alive-but-refusing and does not fail |

**What it does not check, stated plainly so nobody reads its green as more than it is:**

- **It does not re-screen the field.** It cannot tell you that a design system published something
  new, that a licence changed, or that a source you cited now says something different. A link
  that still returns 200 is a live URL and nothing more.
- **It does not judge whether a value is still right.** It verifies that the numbers are internally
  consistent and that the claims about them are backed. Whether hue 262 is still the right accent,
  or 44px still the right row, is a measurement somebody has to take again.
- **It does not look at a rendered screen.** Nothing it runs rasterises anything, so a rule that is
  correct on paper and wrong in a browser passes. `tools/painted.py` paints the certified pairs in a
  browser, and runs only locally.
- **Nothing checks that the book is complete.** The six external taxonomies it was cross-checked
  against on 2026-09-21, and six more never checked, are named in the records above; re-running
  that audit is a deliberate act.

**A field re-screen is a monthly job for a person**, and the green tick on this workflow is not
evidence one happened.

## Re-rendering the component sheets

`tools/components.py --check` fails once `components.css`, `radiogroup.js` or a generated sheet
changes after the renders were stamped, because no tool in `tools/` writes a render. Serve the repository
over localhost (a `file://` page cannot have its stylesheets read by an audit), open each
`components/sheets/<group>.html?theme=light` and `?theme=dark` at 1440 wide, save a full-page WebP
screenshot to `components/renders/<group>-<theme>.webp`, then run `python3 tools/components.py --stamp`.
Headless Brave reports `prefers-reduced-motion: reduce` and a dark colour scheme by default, so a
render or an audit that means the default conditions has to say which it measured. An audit served
that way reads colour from the screenshot, never a canvas: see `painted.py` above.

## Releasing

Before tagging, render every example brand in a browser from its exports, in both themes and
under `prefers-contrast: more`, and look at the three side by side: a component sheet opened as
`components/sheets/<group>.html?brand=<name>&theme=dark`, served over localhost, draws from that
brand's `exports/variables.css` with the vendored faces.
`tools/distinct.py` reports how far apart the brands paint and refuses only one brand built twice;
whether two brands read as two products is a render looked at, which no tool in `tools/` can do:
`painted.py` paints pairs, never a screen ([design/12-brand.md](design/12-brand.md#telling-brands-apart)).
Run `python3 tools/painted.py` too, which certifies every ramp pair on the pixels a browser paints.
